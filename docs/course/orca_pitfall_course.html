先量再信：一个电阻插错的代价

你踩过的坑 项目实录
DIR 下拉电阻 R3 曾经插成 10 kΩ。DIR 输出高电平时，TXB0104 的 B1 脚只有约 3.5 V。换成 100 kΩ 后实测 4.77 V。（HANDOFF.md）

原理

TXB0104 是自动识别方向的电平转换芯片。为了能被对面的信号“推翻”，它的输出故意做得很弱，内部串了大约 4 kΩ 的电阻。公认 你在输出脚上接一个下拉电阻 R，就和这 4 kΩ 组成了分压：

V(B1) = 5 V × R / (R + 4 kΩ)

后面接的 74LVC2G241 在 5 V 供电时，要求输入高电平不低于 0.7 × 5 = 3.5 V。公认 拖动下面的滑块，看 10 kΩ 落在哪里。

实验 · 分压和门槛

10 kΩ 算出来是 3.57 V，离门槛只有 0.07 V。电路能工作，但几乎没有余量。电源低一点、温度变一点、地上有一点噪声，就会时好时坏。这种“刚好能用”比“完全不通”难查得多。

依赖的假设：4 kΩ 是典型值，每颗芯片会有偏差；计算只考虑了这一个负载。结论什么时候失效：换成强驱动的电平转换芯片后，这条限制就不存在了。

新人
  • 手边有 10k 就插 10k，“下拉电阻嘛，差不多”
  • 能通信了就认为电路是对的
  • 数据手册只看引脚图
资深
  • 先翻数据手册的“推荐工作条件”和“应用注意”
  • 每个节点算一遍电平，和门槛比，留至少 20% 余量
  • 上电后量实际电压，写进文档
  • 反过来问：这颗芯片适合这个用途吗？

最后一条值得展开。你的三根信号（DIR、TX、RX）方向都是固定的，并不需要“自动识别方向”。用方向固定的缓冲器做电平转换，驱动强，也没有上下拉电阻和负载电容的限制。做转接 PCB 时可以考虑换掉 TXB0104。我的判断

TXB0104 的数据手册还写了一条：每个输出最多带 70 pF。你在 B1 上接了一个 104（0.1 µF）电容来滤毛刺，会怎样？
0.1 µF 是 100000 pF。4 kΩ × 0.1 µF 的时间常数是 0.4 ms，57600 波特率下一位才 17 µs，DIR 根本来不及翻转。HANDOFF.md 里已经提到这个电容要确认容值，这是一条还没关闭的遗留项。

电源与地：电流走哪条路回去

你踩过的坑 项目实录
地线原来分在两条轨上，只靠一根长跳线连通。现象是应答不正常、发送时 RX 上有回显。把逻辑分析仪的地线和探头接上以后，故障就消失了。最后把所有地都接到同一条轨上才解决。（HANDOFF.md 坑 2）

原理

原理图上的地是一个符号，处处 0 V。实物上的地是一段导线，有电阻。电流流过就有压降：

地线两端的压差 = 流过的电流 × 这段地线的电阻

面包板的一个触点加一根杜邦线，电阻可能有零点几欧。舵机一动就是几百毫安到一两安。于是“舵机的地”和“芯片的地”之间出现了零点几伏的跳动。你的 DIR 信号又是 TXB 弱驱动的，很容易被这个跳动带过门槛，接收通路在发送时被打开，就出现了回显。项目实录

实验 · 地线上的压降

参考：一根好的粗电源线约 10 mΩ，一个面包板触点加杜邦线约 100–300 mΩ。判定用的 50 mV 和 300 mV 是我的经验值，不是标准。电流快速变化时还有电感的作用，实际毛刺比这里算的更大。

“接上仪器就好了”是一条线索

逻辑分析仪的地夹子给两块地之间多搭了一条通路，探头又给 DIR 加了一点电容。测量本身改变了电路。遇到这种现象，资深工程师会直接怀疑两件事：地没接好，或者某个节点驱动太弱。你当时两条都中了。

新人
  • 把地当成 0 V，哪里方便接哪里
  • 电机线和信号线共用一根细地线
  • 故障消失了就继续往下做
资深
  • 接线前先画出电机电流的来回路径
  • 电机电流走独立的粗线，逻辑地在一个点接到电源地
  • 每个芯片电源脚旁边放去耦电容
  • 故障自己消失时，认为它还在，继续找原因

同一个道理用在电源上

17 个电机全部堵转时理论上约 16 A；按 300 mA 限流约 6 A。JST 小插头的额定电流约 3 A，菊花链的第一根线要扛整条链的电流。推算 电压被拉低时，舵机可能自己重启。从电脑那边看，现象是“通信偶尔掉线”，很容易去查软件，方向就错了。

握拳动作做到一半，有两个舵机偶尔掉线，过一秒又回来。最先查什么？
线索有两条：故障和大电流动作同时发生；掉线后能自己回来。这两条都指向供电跌落导致舵机重启。调长超时只是把症状藏起来。量电压要抓最低值，用示波器或万用表的 MIN 记录功能，普通读数看不到瞬间跌落。

半双工时序：TXEN 那 20 微秒

你项目里的坑 项目实录
用 orca_core 配置过舵机链以后，舵机的 Return Delay 从出厂的 500 µs 变成 20 µs。固件必须在最后一个停止位发完后的 20 µs 内把 TXEN 切回接收。（docs/下一步_预紧到换KM1M7C.md 坑 2）你的透传固件是怎么切的，仓库里还没有记录。

原理

DATA 是一根线，主机和舵机轮流说话。TXEN = 1 时你的缓冲器在驱动这根线，TXEN = 0 时放开。舵机收完指令，等一个 Return Delay 就开始回答。公认 所以放开的时刻有一个窗口：

  • 切早了：最后一个字节还没发完就放开，包尾的 CRC 被截断。舵机校验不过，什么都不回。你看到的只是超时。
  • 切晚了：舵机已经开始回答，你还在驱动总线，两边打架。应答开头几个字节丢失，包头没了，解析不出来。

57600 波特率时一位是 17.4 µs，一个字节 174 µs。20 µs 的窗口只比一位长一点。

实验 · 调 TXEN 放开的时刻

模型做了简化：把“停止位结束之前放开”一律算作截断。三个按钮对应三种常见写法。

把 Return Delay 切到 500 µs，再点“延时 1 ms”，仍然失败；把滑块拖到 400 µs 附近就能通过。这解释了一种很典型的经历：固件一个字没改，跑过别人的配置工具后突然不通了。原因是舵机里的参数被改了，窗口从 500 µs 缩到 20 µs。

新人
  • 发完数据加一个 delay，调到能通为止
  • 不知道“缓冲空”和“发送完成”是两个标志
  • 测一次能通就算通过
资深
  • 用 TC 标志；先查 MCU 的串口有没有硬件自动方向控制
  • 逻辑分析仪同时抓 TXEN 和 DATA，量出实际余量
  • 看 1000 次里最坏的那次，不看平均值
  • 想到中断：TC 之后如果被别的中断打断几十微秒，就会偶尔迟到

很多 MCU 的串口带 RS-485 方向控制功能，硬件自动在停止位结束时翻转一个引脚，不受中断影响。KM1M7C 有没有，需要查它的手册。待查

固件用“发送缓冲空”标志切 TXEN。接一个舵机，ping 它，最可能看到什么？
缓冲空的时候，最后一个字节刚进移位寄存器，还要一个字节的时间才发完。这时放开总线，CRC 的高字节被截断。舵机收到坏包，按协议保持沉默。“完全没应答”很容易让人去查接线和 ID，而真正的原因在自己发出去的包尾。逻辑分析仪一抓就能看见。

时间账：先在纸上算，再去实物上量

你项目里的坑 项目实录
M7C 的 USB 虚拟串口不管电脑设多少波特率，舵机侧永远是 57600。orca_core 自动探测时先试 1 Mbps，ping 也能通，于是它认定是 1 Mbps。SDK 按 1 Mbps 算出的超时约 38 ms，实际一次全读要约 62 ms，结果每次都超时。（docs/下一步_预紧到换KM1M7C.md 坑 1）

原理

串口每发一个字节要 10 位（1 起始 + 8 数据 + 1 停止）。所以：

时间 = 字节数 × 10 ÷ 波特率 + 舵机数 × Return Delay

Sync Read 请求  = 14 + 舵机数            字节
每个舵机的应答  = 11 + 读取长度          字节
DynamixelSDK 超时 = 应答字节数 × 10 ÷ 它以为的波特率 + 34 ms

这个坑的本质是：ping 的包很短，在错误的假设下也能过。系统因为错误的原因恰好能用，直到遇到长包才露馅。推算

计算器 · 一轮读写要多久

读 10 字节（位置 + 速度 + 电流），写 4 字节目标位置。没有计入 USB 和 Python 的开销。17 个舵机、57600、20 µs 时结果是 67.7 ms 和 17.2 ms，和 docs/六块M7C方案调研.md 的表一致。

另外两笔容易漏的账

USB 转串口芯片的延迟。FTDI 芯片默认攒 16 ms 才把数据交给电脑，每次往返都可能白等这么久，要在驱动设置里把 Latency Timer 改成 1 ms。公认 你用 U2D2 时已经改过；换成别的转接器要重新检查。

整包转发的延迟。仓库里的 firmware/bridge/ 是把舵机的应答全部收完，再发给电脑。如果电脑一侧也是 57600 的真串口，17 个舵机的应答要先在总线上走 62 ms，再向电脑发 62 ms，合计约 124 ms，超过 SDK 的 96 ms 超时。你现在用的逐字节透传没有这个问题。推算 前提未确认：电脑侧是不是同速真串口；这份固件没上过板

这是一个真实的取舍：整包转发能查 CRC、能精确切 TXEN，代价是多一个包的延迟。解法有两个方向：把电脑侧的速率提高到远高于舵机侧，或者应答改成边收边转。

新人
  • ping 通了就认为配置正确
  • 感觉“有点卡”，但说不出该多快
  • 超时了就把超时调大
资深
  • 动手前算出理论值，写下来
  • 实测和理论对不上的地方，就是问题所在
  • 能自动探测的参数一律写死
  • 用最长的包做验收，不用最短的
理论算出一轮读写 85 ms，实测平均 140 ms。下一步最有价值的是？
多出 55 ms 说明有一笔账没算到。如果它来自 USB 延迟或某个超时在悄悄重试，改 1 Mbps 之后它依然在，那时总线只要 5 ms，这 55 ms 就成了全部。逻辑分析仪量总线，bus_timing.py 量电脑端，两者相减就是中间环节。

中断与共享数据：一年才出一次的 bug

埋在代码里还没爆的坑 项目实录
这一关用的都是 firmware/bridge/bridge.c 的真实代码。它现在在电脑上的测试全过。下面三处在加上“传感器控制”以后才会出问题。

先看写对的地方

static volatile uint16_t s_rx_head;   /* written only by the interrupt */
static volatile uint16_t s_rx_tail;   /* written only by the main loop */

环形缓冲的 head 只有中断写，tail 只有主循环写。每个变量只有一个写者，所以不用关中断也安全。公认

依赖的假设：16 位变量的读写在这颗 32 位 MCU 上是一步完成的。什么时候失效：换到 8 位单片机，16 位变量要分两次读，中间可能被中断改掉一半。

隐患一：两个写者的计数器

int bridge_submit(...) {          /* 放一个包进队列 */
    ...
    s_q_count++;
}
void bridge_poll(void) {          /* 主循环：取一个包发出去 */
    ...
    s_q_count--;
}

现在两个函数都在主循环里调用，没有问题。设计文档说以后传感器控制“每 20 ms 放一个包进队列”。新人很自然会把 bridge_submit() 写进定时器中断。这时 s_q_count 就有了两个写者。s_q_count-- 在机器上是三步：读出来、减一、写回去。点下面的按钮，看中断插在中间会怎样。

单步演示 · 中断插进 s_q_count-- 中间
内存里的 s_q_count = 2主循环的寄存器 R0 = -队列里真实的包数 = 2

这种 bug 只在中断恰好落在那两三条指令之间时发生，可能几天才一次，而且现象和原因离得很远：你看到的是“手的动作偶尔慢半拍”。

三种改法，各有取舍：

  • 中断里只置一个标志，主循环看到标志再提交。最简单，你的设计文档画的就是这种。代价是提交时刻有一点抖动。推荐
  • 改计数时短暂关中断。通用做法。代价是关中断期间会影响别的中断的响应，比如第 3 关的 TXEN。
  • 去掉计数器，只用 head 和 tail。和上面的环形缓冲一样，每个变量一个写者。代价是队列要空一格。

隐患二：悄悄丢掉的字节

void bridge_pc_rx_isr(uint8_t byte) {
    uint16_t next = (s_rx_head + 1) & (BRIDGE_PC_RX_BUF - 1);
    if (next == s_rx_tail) return;           /* full: drop the byte */
    ...

缓冲满了就丢字节，这个处理本身合理。问题是它没有留下任何痕迹。统计结构里有 CRC 错、超时、队列满、无应答五个计数器，唯独没有“缓冲溢出”。将来真的丢了，你只会看到下游的“偶尔 CRC 错”，然后去查线、查干扰。

规则：每一条“丢弃”和“放弃”的分支，都要有一个计数器。写一行代码，省几天排查。我的判断

隐患三：阻塞和时钟粒度

run_transaction() 在等应答时不返回。普通事务等到总线安静 3 ms，广播 ping 固定等 800 ms。现在只转发电脑的包，没有问题。加上 20 ms 的控制周期以后，一次广播 ping 会让控制停 800 ms，手保持着上一个目标不动。

还有一笔小账：“安静 3 ms 就算应答结束”意味着每个事务固定多付 3 ms。57600 时全读要 68 ms，可以忽略。1 Mbps 时全读只要 4 ms，这 3 ms 就占了将近一半。推算 到那时要改成按应答长度收，收够就结束。

新人
  • 变量在中断和主循环里都用，加个 volatile 就放心了
  • 测试通过就认为没有竞争问题
  • 出错分支写 return 了事
资深
  • 给每个共享变量标明谁写、谁读，写进注释
  • 知道 volatile 只保证每次都去读内存，不保证“读改写”不被打断
  • 竞争问题靠读代码推理，不靠测试碰运气
  • 在头文件里写清楚：这个函数能不能在中断里调用
给 s_q_count 加上 volatile，能解决隐患一吗？
volatile 只告诉编译器“这个变量随时可能变，每次用都要重新读，不要缓存”。它不会把三步合成一步。要保证一段操作不被打断，得靠“只有一个写者”的结构，或者关中断。

协议与故障：让错误看得见

埋在代码里还没爆的坑 项目实录
firmware/dxl/dxl.c 判断应答是否出错的那一行，把错误字节的最高位屏蔽掉了： 
return (s_rx[IDX_ERR] & 0x7F) ? DXL_ERR_STATUS : DXL_OK;

原理

Protocol 2.0 的应答包里有一个错误字节。低 7 位是这条指令的错误码。最高位叫 Alert，表示舵机自己出了硬件故障：过载、过热、电压异常。公认 Alert 置位后，要去读地址 70 的 Hardware Error Status 才知道具体是哪一种。

X 系列舵机发生过载后会自动关掉扭矩，之后写目标位置它也不动，要发 Reboot 指令才恢复。公认 腱绳手顶到限位时，过载是最常见的故障。按现在的代码，这时驱动返回 DXL_OK，一切看起来正常，只是手不动。

工具 · 应答包解码

点“带 Alert 的应答”，错误字节是 80。按 & 0x7F 算，结果是 0，被当成正常。

藏在舵机里的状态

舵机控制表的前 64 个地址存在 EEPROM 里，掉电不丢：ID、波特率、Return Delay、运行模式、方向、各种限制。公认 这些值会被任何连过它的软件改掉。第 3 关的 Return Delay 就是这样变的。

资深的做法是把“我期望的配置”写成一张表，每次上电先把 17 个舵机的这些值读回来比对，对不上就拒绝启动，并说清楚是哪个舵机的哪一项。你的 bus_timing.py 已经会读 Return Delay，把它扩展一下就是启动自检。

改不回来的操作，先验证退路

把 17 个舵机从 57600 改到 1 Mbps，改到第 9 个时出错，总线上就有两种波特率。你的文档里已经写了对策：先确认能用 U2D2 和 Wizard 把舵机救回来，再动手。这条原则可以推广到所有写 EEPROM、刷固件、改硬件的操作。

新人
  • 只判断“通信成功了没有”
  • 读失败时继续用上一次的数值
  • 直接开始改，出事了再想办法
资深
  • 区分三层：通信通不通、指令对不对、设备本身好不好
  • 数据带上“是否新鲜”的标记，过期数据不进控制
  • 上电自检，把隐藏状态变成明面上的检查
  • 动手前先演练一遍恢复步骤
握拳后有一根手指松开了，再发指令也不动。ping 它有应答。最可能的原因和处理是？
通信正常说明线和电源都在。扭矩没了但舵机活着，这是保护动作的特征。先读地址 70 花一秒钟，拆手要一小时。如果确认是过载，要回答“为什么会过载”：腱绳太紧、关节卡住，还是电流限制设得不对。直接 Reboot 再跑只会再来一次。

会动的东西：软件能撤销，机械不能

你踩过的坑 项目实录
小角度测试都正常。测最大活动范围时，中指外展腱绳的结被拉穿了孔，掉进手掌通道。当时用的是官方默认的 300 mA。修复花了好几天。（docs/遇到问题/中指ABD腱绳脱出.md）

原理

关节顶到机械限位以后，位置控制会让电机一直用上限电流拉。这个力全部压在腱绳的结上。软件写错了可以回退一个版本；结拉穿了要拆手。两种错误的代价差了几个数量级，所以对待方式也该不同。

做法叫分级放能量：每次只把一个量放大一级，确认没有异常再放下一级。

维度第一级第二级第三级
电流上限60 mA150 mA300 mA
运动范围中立位附近 ±10%一半行程全行程
运动对象一个关节一根手指整只手
速度慢，看得清正常演示速度

60 → 150 → 300 mA 这个台阶，你在 docs/腱绳收紧确认.md 的单舵机实验里已经用过。出事的那次是直接在 300 mA 下跑全行程，跳过了前两级。

依赖的假设：小电流下能暴露的问题，大电流下同样存在。什么时候失效：有些问题只在大力时出现，比如结慢慢滑动。所以每一级都要盯着电流读数和声音，在最高一级停留久一点。

失效安全：电脑不在了，手怎么办

Python 程序崩溃、USB 被碰掉、电脑休眠。这时舵机保持着最后一个目标位置继续出力，时间长了会发热。X 系列舵机有 Bus Watchdog 功能（地址 98）：超过设定时间没收到指令，舵机自己停下来。公认 启用前请在 e-Manual 里核对你的型号和单位

“停下来”对一只手意味着什么，没有标准答案。关扭矩，手会松开，拿着的东西会掉。保持位置，电机会一直发热。这需要事先决定并写下来。你的六块 M7C 调研里已经提出了这个问题，还没有答案。

新人
  • 装好就想看完整演示
  • 用默认参数，“官方的应该没问题”
  • 没想过程序崩了硬件会怎样
资深
  • 上电前问三句：最坏会坏什么？能不能修？修多久？
  • 第一次运行时，一只手放在电源开关上
  • 每个新动作都从最低一级开始
  • 为“通信断了”设计好行为，并且实际拔线测一次
你刚换了一根腱绳。下面哪个顺序最稳妥？
标定的原理是让电机顶到限位，它本身就是一次全行程加上限电流的测试，正好是出事那次的条件。断电用手扳不需要任何能量，却能发现绳子走错槽、结没卡住这类问题。越便宜、越安全的检查越要放在前面。
“官方默认参数下出的事，所以不是我的问题。”这句话哪里不对？
你的事故记录里已经分析到了这一点：v2.1 加了 PTFE 管并且调整了各关节的标定电流。默认值附带着一组前提条件。用别人的参数之前，先确认自己的硬件满足这些前提；不确定时从更保守的值开始。

系统设计：六块 M7C 怎么分

你正在做的事 项目实录
下一个任务是用 6 块 M7C 控制这只手，一根手指一块。调研已经写好（docs/六块M7C方案调研.md），还没动手。这一关把那份调研当作案例，看资深工程师在动手之前想些什么。

第一问：到底要解决什么

如果目的是“更快”，把现在的单总线提到 1 Mbps 就够了，不用加板子。分成六块真正带来的是故障隔离、走线变短、以后每根手指可以本地控制。目的不同，方案就不同。新人拿到任务就开始做；资深会先把目的问清楚，再带着两三个方案和各自的代价回去讨论。

对比 · 一轮读写的时间

分组按调研：五条总线各 3 个电机，一条 2 个。理论值，不含 USB 和电脑端开销。

六条总线轮流跑，比现在的单总线还慢，因为每条总线都要付一次包头和往返的固定开销。只有六条同时跑才有收益。所以电脑端的并行是硬要求。

分开以后新出现的问题

问题单总线时六总线时对策
地线一处接地六块板同时连着 USB 地和电机地，形成环路第 2 关的做法：电机电流走独立粗线，逻辑地单点接
COM 号一个，写死也行换个 USB 口，食指和小指就可能对调连接时逐个 ping，按回答的 ID 认板子，对不上就拒绝启动
部分故障要么全通要么全断可能五根手指在动，一根掉线事先定好策略并测试（第 7 关）
同时性一个 Sync Write 同时生效六条总线之间差 1–2 ms 推测用逻辑分析仪量出来，再判断要不要管
DATA 隔离不存在共用一块 PHB 可能把六条总线连在一起 推测接线前断电量通断

规律：把一个东西拆成多个，会产生一批“它们之间”的问题。同步、识别、部分失效，这些在单个的时候都不存在。做方案对比时，这一类成本最容易被漏算。

先做哪一步

调研里的实施顺序，第一步是只分两条：把食指拆到第二块 M7C，其余不动。这一步花费最小，却能同时检验固件能否复用、地线有没有问题、合成软件能不能工作。

这是一种排序方法：先做最能消除不确定性的那一步。新人常按“先做容易的”或“先做最有成就感的”来排，比如先画六路 PCB。结果板子打回来才发现方案有问题。

新人
  • 领导说六块板，就开始接六块板
  • 只比较方案的优点
  • 先做完硬件，再写软件，最后联调
资深
  • 先确认目的，带着方案对比去沟通
  • 给每个方案问四句：坏一块会怎样？怎么调试？怎么退回去？会不会堵死以后的路？
  • 用最小的一步验证最大的未知
  • 把“推测”列成清单，逐条变成“实测”
六块板都接好了，演示时食指和小指的动作对调了。根本原因最可能是什么？
COM 号由操作系统分配，换 USB 口、换电脑、甚至重启后都可能变。它不是板子的身份。能当身份用的是板子自己能回答的东西：总线上舵机的 ID。按 ID 认板子以后，线随便插都不会错。

工程纪律：让三个月后的人看得懂

项目当前最大的一条风险 项目实录 我的判断
让这只手动起来的透传固件不在仓库里。11 月 4 日换 M7C 时的改动是在另一台电脑上做的，docs/换M7C_一页纸.md 的“实际改动”一节还空着。仓库里的 firmware/bridge/ 是另一份代码，没有上过板。

为什么这件事重要

现在如果那块 M7C 坏了，或者那台电脑的硬盘坏了，这只手就回不到“能动”的状态，要重新摸索一遍。第 8 关要把同一份固件烧进六块板，更需要一份确定的、可重建的版本。

标准只有一条：一个没参与过的人，只拿到仓库，能不能把板子恢复到现在的状态？要做到，需要这些东西都在仓库里：

  • 固件源码和 Keil 工程文件
  • 编译器版本、芯片包版本
  • 烧录步骤，用哪个工具、哪些选项
  • 引脚分配：哪个串口接哪里，TXEN 是哪个引脚
  • 给能跑的版本打一个标签，比如“2026-11-04 手第一次用 M7C 动起来”

再进一步：让固件能回答“你是哪个版本”。上电时从调试串口打印版本号和编译日期。六块板里有一块行为不一样时，这一行能省很多时间。

你已经做对的

HANDOFF.md 记录了每一步的状态和踩过的坑；调研文档把结论分成“源码确认、算出来的、推测、没有验证”；数据包用脚本生成而不手算；驱动有电脑上跑的测试。腱绳事故的记录按“现象、原因、已排除、处理、预防”写，这正是业内事后复盘的格式。保持下去。

新人

  • 文档写“已完成”，不写怎么验证的

一个可以一直用的方法

每次卡住超过半小时，解决以后花十分钟写下四行：现象是什么；我最初以为是什么；实际是什么；怎样能更早发现。攒到五十条时回头看，你会发现大部分问题落在少数几类里。那几类就是你自己的经验。
