## 结论

- **你的想法是对的**：一块板一个 COM，一个 COM 一个串口对象。要补的是上面一层，把 N 个串口合成“一只手”。
- **推荐做法（也是最主流的做法）**：写一个 `MultiBusClient`，插在 `OrcaHand` 和串口之间。`OrcaHand`、官方脚本、orca_ui、`calibration.yaml` 都不改。
- **并行**：一条总线一个线程，用线程池同时发、同时等，全部回来再合并。2 块板时一轮理论上约 19 ms；轮流跑是约 38 ms。
- **2 块和 6 块用同一份代码**：板数、分组都写在一张路由表里，从 2 块到 6 块只是表多几行。
- **读源码新发现的 3 个坑**（上一份调研没写到）：
  1. 官方的连接探测只 ping 第一个和最后一个 ID（1 和 17）。食指那条总线（7、8、9）上两个都没有，按官方流程会直接报“没有电机应答”。
  2. `MotorClient` 现在有 49 个公开方法（上一份调研时估的 200–300 行偏少了）。
  3. `Start-ORCA.bat` 每次启动都会把 orca_core 拉到最新，而官方接口变得很快。合成层写好以后要把 orca_core 固定在一个版本上。

## 1. 整体结构

```
官方脚本 / orca_ui / 你自己的程序        （不改）
            │
        OrcaHand                        （不改）关节角、标定、手势
            │  一次只放进来一个调用（它自己有一把锁）
     MultiBusClient                     （新写）路由、拆分、并行、合并
      ├─ 总线“食指” → DynamixelClient(ID 7,8,9,   COM a) ── 线程 1
      └─ 总线“中指” → DynamixelClient(ID 6,17,2,  COM b) ── 线程 2
            │                    │
          M7C-1                M7C-2      （透传固件，不改）
```

**为什么插在这一层**：orca_core 里所有电机读写都经过 `MotorClient` 这一个接口。上面的 `OrcaHand` 只说“读全部位置”“把这几个 ID 写到这些位置”，不关心有几个串口。所以只要新写的东西对上面看起来还是“一个 `MotorClient`”，上面就都不用动。

**为什么下面直接用官方的 `DynamixelClient`**：每个 `DynamixelClient` 都有自己的串口对象和自己的锁（`dynamixel_client.py` 283–288 行），互相不共享状态，所以开 N 个放进 N 个线程是安全的。超时重试、Fast Sync Read、报警处理这些都已经写好了，不用重写。

## 2. 三个方向和取舍

| | A. 合成客户端（**推荐，最主流**） | B. 每块板一个 OrcaHand | C. 电脑上做“虚拟网关” |
|---|---|---|---|
| 做法 | 一个 `OrcaHand`，下面挂 N 条总线 | N 个 `OrcaHand`，每个带一份只含自己手指的 config | 单独一个程序占住 N 个 COM，对外假装成 1 个 COM |
| orca_core | 不改 | 不改 | 完全不知情 |
| 官方脚本、UI | 照常用 | 只能一根手指一根手指地用 | 照常用 |
| 标定文件 | 沿用现在这一份 | 要拆成 N 份 | 沿用 |
| 整手手势 | 照常 | 要自己再写一层去凑 | 照常 |
| 要写的东西 | 合成层（接口多，约 49 个方法要分类处理） | 很少，但拇指被拆到两块板上会很别扭 | 最多：要拆包、拼包，还要装虚拟串口驱动 |
| 最大的风险 | 官方接口变了要跟着改 | 越往后越乱 | Sync Read 的应答要自己拼，最容易出错 |
| 适合 | 现在，以及 6 块 | 只想今天让两根手指各自动一下 | 以后给 MCU 网关固件打样 |

**取舍**：
- A 的代价是要把官方接口整个包一遍，好处是上面全都不动，2 块到 6 块不用重写。
- B 起步最快，但它把“一只手”拆成了 N 只手。到 6 块时，拇指 4 个电机分在两块板上，手势和标定都要自己拼，不建议作为正式方案。
- C 的逻辑和以后“MCU 网关 + CAN-FD”（调研里的方案 B）是同一件事，将来有参考价值，现在做太早。

## 3. 并行怎么做

**原理**：每条总线是半双工，一问一答，时间主要花在“等线上的字节”上。等的时候线程是闲着的。所以让 N 条总线各自有一个线程，同时发出去、同时等，总时间就等于最慢的那一条，而不是 N 条相加。

**做法**：

```python
# 示意，不是最终代码
from concurrent.futures import ThreadPoolExecutor

pool = ThreadPoolExecutor(max_workers=总线数)

def 读全部():
    结果们 = list(pool.map(lambda 总线: 总线.read_position_velocity_current(), 总线们))
    # 全部回来以后，按电机 ID 放回 config 里规定的顺序
    return 合并(结果们)
```

**三种并行方式的取舍**：

| | 线程（**推荐，最主流**） | asyncio | 多进程 |
|---|---|---|---|
| 能不能直接用官方 `DynamixelClient` | 能 | 不能，官方 SDK 是阻塞式的，要重写 | 能 |
| 复杂度 | 低 | 高 | 中，进程间要传数据 |
| 什么时候才需要 | 现在 | 基本不需要 | 提到 1 Mbps 以后如果线程不够快再考虑 |

**时间账**（理论值，沿用调研第 2 节的算法，57600、每条 3 个电机）：

| | 一轮读 + 写 |
|---|---|
| 现在：单总线 17 个 | 约 85 ms |
| 2 条总线**轮流** | 约 38 ms |
| 2 条总线**同时** | 约 19 ms |
| 6 条总线同时 | 约 19 ms |
| 6 条总线轮流 | 约 114 ms（比现在还慢） |

**依赖的假设**：
- Python 的线程在等串口时会让出解释器，所以多条总线的“等”可以重叠。这是 Python 的公认行为；但 Windows 上你这套 USB 串口实际能重叠多少，要实测。
- 57600 时一轮 19 ms，线程切换的开销（零点几毫秒）可以忽略。提到 1 Mbps 后一轮只有 1 ms 左右，线程和 USB 的开销就成了大头，那时并行的好处会小很多。

## 4. 四类调用怎么处理

`MotorClient` 现在有 49 个公开方法（其中 10 个是必须实现的抽象方法）。不用一个一个想，分成四类，每类一个处理办法：

| 类 | 例子 | 处理 |
|---|---|---|
| ① 读全部 | `read_position_velocity_current`、`read_temperature` | 并行发给所有总线，回来后按 ID 放回原来的顺序 |
| ② 带 ID 列表的写 | `write_desired_pos`、`write_desired_current`、`set_torque_enabled`、`set_operating_mode` | 按路由表把列表拆成几份，并行发 |
| ③ 单个电机 | `read_hardware_error`、`reboot_motor`、`hold_motor_off` | 查路由表，只发给那一条 |
| ④ 整体状态 | `connect`、`disconnect`、`last_read_ok`、`responding_motor_ids` | 全部都做；成功 = 全部成功；应答名单 = 各条的并集 |

**三条不能错的规则**：
1. **顺序**：读回来的数组必须按 config 里 `motor_ids` 的顺序（1–17）。上层是按位置取数的，顺序错了手指就对不上。
2. **新鲜度**：`last_read_ok` 必须是“这一次读，所有总线都成功”。只要有一条失败就算失败，上层会自己丢掉这次数据。
3. **类属性**：`OrcaHand` 连接后会按客户端的类型取默认电流等参数（`hardware_hand.py` 334 行）。合成类要带上 `DynamixelClient` 的那些类属性，否则默认电流会错。

**没接的电机**：2 块板阶段只有 6 个电机在线。官方代码本来就支持“电机不在线就跳过”（连接时 ping 一遍，之后只读写应答了的），合成层只要把“没有任何总线负责的 ID”报成不在线就行。

## 5. 路由表和 COM 识别

单独放一个文件，不改官方 config：

```yaml
# tools/orca/multibus/buses.yaml（示意）
baudrate: 57600
buses:
  index:  [7, 8, 9]     # 食指
  middle: [6, 17, 2]    # 中指
# 以后加：ring / pinky / thumb / wrist_cmc
```

**不写 COM 号**。启动时把电脑上的 COM 逐个打开，ping 一遍 1–17，谁回答了 7、8、9，谁就是食指那条。然后和这张表对一遍：

- 完全对上：继续。
- 某个 COM 上的 ID 跨了两组、某组没找到、同一个 ID 出现在两个 COM：**拒绝启动，并说清楚哪里不对**。

**为什么**：Windows 的 COM 号会随着插哪个 USB 口变。如果 6 块板的 USB 序列号一样，号还可能互换。写死 COM 号的话，换个口就可能把食指的指令发给中指。按 ID 认总线就没有这个问题。

## 6. 怎么接进 orca_core 而不改它

`OrcaHand` 里有两个专门留出来的方法：

- `_create_motor_client()`：造客户端的地方。
- `_resolve_motor_driver()` / `_trial_probe()`：连接时探测电机型号和波特率的地方。

官方自己的 `MockOrcaHand` 就是靠覆盖这两处做出来的（`MockMotorResolutionMixin`），所以这是官方认可的扩展方式。

做法：写一个启动脚本 `run.py`，先把这两处换成我们的（造 `MultiBusClient`；探测直接返回 dynamixel + 57600），再去运行官方脚本。用法大致是：

```bat
uv run python <whj_MCU>\tools\orca\multibus\run.py scripts\neutral.py %CFG%
```

**探测为什么必须绕过**：官方 `probe` 只 ping `motor_ids` 的第一个和最后一个，也就是 1 和 17。食指总线上是 7、8、9，两个都没有，会报“no motor responded”。中指总线上碰巧有 17，会通过，这种一条过一条不过的现象很容易误导排查。

**要在仓库里新增的文件**（都在 `tools/orca/multibus/`）：

| 文件 | 内容 |
|---|---|
| `buses.yaml` | 路由表 |
| `multibus_client.py` | 合成层 |
| `run.py` | 启动脚本 |
| `test_multibus.py` | 用官方的 `MockDynamixelClient` 测，不接硬件 |
| `Start-MultiBus.bat` | Windows 一键启动，先检查 main 更新 |

## 7. 一条总线掉线时怎么办

单总线时不存在这个问题：线断了就全停。多总线时可能食指掉了、中指还在动。要事先定规则。

| 策略 | 做法 | 取舍 |
|---|---|---|
| 全部松手（**推荐先用这个**） | 任何一条连续失败 N 次，其余总线全部关扭矩，然后报错 | 最安全，腱绳手关扭矩就是松开；但手里的东西会掉 |
| 全部保持 | 其余总线不再发新指令，停在当前位置 | 不掉东西；但如果正夹着什么，会一直夹着 |
| 继续动 | 其余手指照常 | 不建议：上层以为整只手在动，实际少一根 |

另外，一条总线超时会拖慢整轮（要等它超时才能合并）。所以连续失败几次以后要把这条标成“已掉线”，不再等它。

## 8. 从 2 块到 6 块

| 步 | 内容 | 过关标准 |
|---|---|---|
| 1 | 写合成层，用 Mock 测 | 四类调用的测试都过；路由表对不上时拒绝启动 |
| 2 | 接 2 块板（食指、中指），其余 11 个电机不接 | 两个 COM 被自动认对；`manual_control` 能分别动两根手指 |
| 3 | 用 `bus_timing.py` 比较“轮流”和“同时” | 同时的一轮时间接近单条的时间，失败 0 次 |
| 4 | 拔掉一条 USB | 另一根手指按第 7 节的策略停住 |
| 5 | `buses.yaml` 加到 6 行 | 代码不改 |

**为下一步留的口子**：合成层只通过“总线”这个对象和下面打交道。以后 M7C 上做本地控制、不再是透传时，只要换“总线”的实现（从“发 Dynamixel 包”换成“发你自己的协议”），上面的路由、并行、合并都不用动。

## 9. 这个设计在什么条件下会失效

- **USB 这一段不能并行**：如果几块板的虚拟串口实际上共用一个轮询通道，或者驱动有十几毫秒的延迟定时器（FTDI 默认 16 ms），并行的好处会被吃掉。M7C 是怎么连到电脑的，到现在还不清楚（调研第 7 节问题 2）。
- **官方接口变了**：合成层是按 `48a3856` 的接口设计的。官方一改接口，合成层可能就缺方法。对策：把 orca_core 固定在一个提交上，升级时先跑 Mock 测试。
- **需要多根手指严格同时动**：单总线的 Sync Write 是同一时刻生效的；多总线之间会差一点（估计 1–2 ms）。做手势没问题，做很快的协调动作时要注意。
- **提到 1 Mbps 以后**：一轮只有 1 ms 左右，线程方式的开销占比变大，这时分总线对“速度”的意义不大，意义主要在故障隔离和以后的本地控制。
