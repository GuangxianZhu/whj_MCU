# 上机清单：两块 M7C 控制两根手指

日期：2026-11-15。目标：食指（ID 7、8、9）和中指（ID 6、17、2）各由一块 M7C 控制，能标定、能预紧、能一起开合。
`<whj_MCU>` 指你电脑上本仓库的文件夹。所有命令都在 **orca_core 文件夹**里运行。

**先说清楚**：软件我用两种办法测过，但都不是真机。
1. 假电机（官方自带的 Mock）。
2. 模拟串口：串口换成假的，按 Dynamixel 协议逐字节应答；上面跑的是**官方真正的驱动和 SDK**。这一层能测到真机才会走到的代码。

没有测过的只剩真实 USB 串口这一段。所以清单的顺序是：先用不会动的命令确认接线和串口，再让手指动。

---

## 第 1 步：断电检查接线（万用表蜂鸣档，约 5 分钟）

你的接法应该是这样的（一块电源板、两条数据线）：

```
12V 电源 ── 电源板 ──┬── VDD、GND ──> 食指 3 个舵机（7、8、9 串在一起）
                     └── VDD、GND ──> 中指 3 个舵机（6、17、2 串在一起）

电脑 USB ── M7C-1 ── TTL 电路 1 ── DATA-1 ──> 食指舵机的 DATA
电脑 USB ── M7C-2 ── TTL 电路 2 ── DATA-2 ──> 中指舵机的 DATA

TTL 电路 1 的 GND ──┐
TTL 电路 2 的 GND ──┴── 电源板的 GND（三处的地必须连在一起）
```

舵机 3 针插头的脚序：1 GND、2 VDD、3 DATA。

| 量什么 | 应该是 | 不对说明什么 |
|---|---|---|
| **DATA-1 对 DATA-2** | **不响** | **两条数据线连在一起了，最可能是经过电源板**（见下） |
| DATA-1 对 GND、DATA-2 对 GND | 不响 | 数据线对地短路 |
| DATA-1 对 VDD、DATA-2 对 VDD | 不响 | 数据线碰到了 12V，**通电会烧 TTL 电路** |
| TTL 电路 1 的 GND 对电源板 GND | 响 | 没共地，通信会时好时坏 |
| TTL 电路 2 的 GND 对电源板 GND | 响 | 同上 |
| 电源板 VDD 对 TTL 电路的 5V、3.3V | 不响 | 12V 会灌进面包板 |

**最容易出错的一处：电源板会把数据线连起来。**
电源板上那几个 3 针 TTL 口，三根针（GND、VDD、DATA）是全部并在一起的。依据：你 10 月做“工作一”时，U2D2 插电源板的一个口、舵机插另一个口，就能通信，说明数据是经电源板从一个口通到另一个口的。
所以如果两根手指都用完整的 3 芯线插在电源板上，它们的 DATA 就在电源板上连成了一条线，两块 M7C 会抢同一条线。
做法：从电源板到手指的线**只留 GND 和 VDD 两根**，第 3 根 DATA 不要接到电源板上。

其余 11 个舵机怎么办：留在电源板上或者拔掉都可以，软件会把它们当作“没插”。只要保证食指、中指的 DATA 不经过电源板就行。

**通电顺序**：全部接好再开电源板的开关；通电时不要插拔舵机线。

## 第 2 步：拿到文件，改 orca_core（约 10 分钟）

```bat
cd <whj_MCU>
git pull

cd <orca_core 文件夹>
git status
git log -1 --format=%h
```

- `git status` 里出现 `config.yaml`、`calibration.yaml`、`local_config.yaml` 是正常的，那是你自己的设置。
- 如果出现 **`orca_core/hardware_hand.py`**，说明这个文件以前被改过，补丁可能打不上，直接用 `改动说明.md` 第 2 节的“方法二：手动改”。
- 版本号是 `e7a8540`、`f311073`、`12b4db9`、`48a3856` 之一都可以，**不用换版本**，这四个我都试过。

**先备份**（标定会改写 `calibration.yaml`）：把你平时用的 `config.yaml` 所在的整个文件夹复制一份到桌面。

改 orca_core，两种办法做一种即可，结果完全一样：

**办法 A：手动改（想弄懂改了什么就用这个）。** 照 `改动说明.md` 第 2 节“方法二”做：复制 3 个文件，再在 `hardware_hand.py` 里粘贴 3 段。
改完用下面这条命令核对。它把你改的结果和补丁比较，**没有任何输出就说明你改得和补丁一模一样**：

```bat
git apply -R --check <whj_MCU>\tools\orca\multibus\multibus.patch
```

有输出说明某一处和补丁不一样。先跑下面的自检：如果显示 `47 passed`，说明功能是对的，差别只是空格或换行符，可以直接用。
自检不过（多半是空格数不对或者贴错了位置）时，最省事的是撤掉自己的改动、改用办法 B：

```bat
git checkout orca_core\hardware_hand.py
del orca_core\hardware\multibus_client.py tests\test_multibus_client.py tests\test_multibus_wire_level.py
```

**办法 B：用补丁。**

```bat
git apply --check <whj_MCU>\tools\orca\multibus\multibus.patch
git apply <whj_MCU>\tools\orca\multibus\multibus.patch
```

第一条没有任何输出，再跑第二条。

自检（不接硬件，约 15 秒）：

```bat
uv run --group dev pytest tests\test_multibus_client.py tests\test_multibus_wire_level.py
```

应该显示 `47 passed`。
如果这条命令因为公司网络装不了测试工具而失败，可以跳过，不影响使用（这 47 个测试我在四个版本上都跑过）。

## 第 3 步：通电，只读检查（不会动）

```bat
set CFG=<你平时用的 config.yaml 的完整路径>
uv run python <whj_MCU>\tools\orca\multibus\check_buses.py <whj_MCU>\tools\orca\multibus\buses.yaml
```

这个工具只 ping，不开扭矩，不写任何东西。正常的结尾是：

```
  OK: bus 'index' [7, 8, 9] is on COM5
  OK: bus 'middle' [6, 17, 2] is on COM6
...
RESULT: OK
```

它还会打印一份**填好 COM 号的 buses.yaml**，下一步要用。

| 看到 | 意思 | 怎么办 |
|---|---|---|
| `answer on more than one port` | 两条 DATA 连在一起了 | 回第 1 步，查电源板那根线 |
| `no motor answered on any port` | 谁都没回答 | 12V 开了没有；DATA、GND 接了没有；有没有别的程序（串口助手）占着 COM |
| `bus 'middle' ...: no port answered for it` | 中指那块板不通 | 只查那一块：USB、DATA、GND |
| `IDs [9] do not answer` | 那根手指上有一个舵机没回答 | 手指内部串联的线松了 |
| `not probed (not USB)` 而且你的 COM 在里面 | M7C 的串口没被当成 USB 串口 | 加 `--ports COM5 COM6` 再跑 |
| 回答的 ID 和表里不一样 | 你手上的 ID 分组和我写的不同 | 把输出发给我，或者照实际改 `buses.yaml` |

## 第 4 步：改两个设置文件

**(a)** 在 `config.yaml` 同一个文件夹里新建 `buses.yaml`，内容用第 3 步打印出来的那一份（COM 号换成你的）：

```yaml
baudrate: 1000000
buses:
  index: {ids: [7, 8, 9], port: COM5}
  middle: {ids: [6, 17, 2], port: COM6}
```

为什么把 COM 号写死：这样软件不用去试别的串口，每块板只和自己的 3 个舵机说话，和你现在单块 M7C 能用的情况最接近，未知数最少。
COM 号写反了也不会动错手指：软件会发现那个口上没有那几个 ID，拒绝启动，并提示你对调。

**(b)** 在 `config.yaml` 里只改一行：

```yaml
port: multibus
```

其它行（`motor_type`、`hardware_version` 等）不要动。`config.yaml` 里不要写中文。

## 第 5 步：连接并读数（不会动）

```bat
uv run python <whj_MCU>\tools\orca\bus_timing.py %CFG%
```

要看到这几行：

```
multibus: index=COM5 [7, 8, 9], middle=COM6 [6, 17, 2]
connect: True Connection successful (dynamixel @ multibus, 1000000 baud)
motors configured=17  absent=[1, 3, 4, 5, 10, 11, 12, 13, 14, 15, 16]
...
stale / failed reads: 0  (should be 0)
```

会有几行黄色警告说其余 11 个关节没有应答，这是正常的。
把“mean … ms”那一行记下来，这就是两块板轮流读一轮的实际时间。

## 第 6 步：两根手指一起动

先用小角度：

```bat
uv run python <whj_MCU>\tools\orca\multibus\two_finger_demo.py %CFG% --close-deg 25 --cycles 2
```

它做的事：连接 → 开扭矩 → 中立位 → 两根手指的 MCP、PIP 一起弯到 25° 再张开，重复 2 次 → 中立位 → 关扭矩。
随时按 Ctrl+C 停止，停止时会关扭矩。没有标定文件时它会拒绝运行，不会自己去标定。

正常以后再加大：`--close-deg 50 --cycles 5`。角度会被 `config.yaml` 里的关节范围限制住。

也可以用官方的：

```bat
uv run python scripts\neutral.py %CFG%
uv run python scripts\manual_control.py %CFG%
```

## 第 7 步：标定和预紧（需要时才做）

以前整只手的标定仍然有效，只要没重新穿腱绳、没动预紧，就不用重新标定。要做的话：

```bat
uv run python scripts\calibrate.py %CFG% --fingers index middle
uv run python scripts\tension.py %CFG%
```

- 标定只驱动这两根手指，会把关节推到机械限位，和以前一样。其余手指在 `calibration.yaml` 里的数值保持不变（我测过）。
- `tension.py` 只拉住在线的这两根手指的电机，按 Ctrl+C 结束。
- 不带 `--fingers` 也可以，没应答的关节会被自动跳过。

## 出了问题怎么退回去

| 想退到 | 做法 |
|---|---|
| 单块 M7C 或 U2D2（今天之前的用法） | `config.yaml` 的 `port:` 改回原来的 COM 号。补丁不用撤，它只在 `port: multibus` 时起作用 |
| 完全撤掉补丁 | `git apply -R <whj_MCU>\tools\orca\multibus\multibus.patch` |
| 标定被弄乱了 | 用第 2 步备份的文件夹覆盖回去 |

## 我认为最可能出错的地方（按可能性排）

1. **数据线经电源板连在一起。** 第 1 步的蜂鸣测试和第 3 步的工具都能查出来。
2. **补丁打不上。** 原因会是 `hardware_hand.py` 被改过，或者换行符不一致。改用手动方法，只有 3 处粘贴。
3. **M7C 的串口不被识别为 USB 串口。** 只影响自动认 COM；第 4 步已经把 COM 号写死，绕开了。
4. **一块板没共地。** 表现是那根手指时通时不通、读数失败次数不为 0。
5. **ID 分组和我写的不一样。** 我用的是官方左手 v2 的表（食指 7/8/9，中指 6/17/2）。第 3 步的输出会直接显示每个 COM 上实际有哪些 ID。
6. **11-04 那次改动。** 另一个 Claude 在你电脑上改过什么我不知道。如果当时改的是固件或 config，没有影响；如果改了 orca_core 的代码，见第 2 条。
7. **中途拔掉一块板。** 这根手指会停在原地，另一根继续工作，读数会被标成不可靠。软件还没有“一块掉线就全部停下”的保护，测试时手放在 12V 开关旁边。
